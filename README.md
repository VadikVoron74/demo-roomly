## Запуск автотестов

Через Docker:

```bash
docker compose run --build --rm tests
```

Без Docker:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m playwright install chromium
python -m pytest
```

## Автотесты

Три тестовые функции в `tests/test_booking.py`:

| Тест | Что проверяет |
|---|---|
| `test_successful_booking` | Позитивный: валидная бронь, показано сообщение «Бронирование создано.» с комнатой, датой, временем и именем |
| `test_required_field_is_empty` | Негативный: параметризован по 7 обязательным полям. В каждом запуске пустым остаётся одно поле, остальные валидны. Проверяются ошибка под полем, общее сообщение формы и отсутствие сообщения об успехе |
| `test_discovered_defect` | Дефект BUG-03 (бронь больше 4 часов принимается): `xfail(strict=True, reason="BUG-03: Можно забронировать комнату более, чем на 4 часа", raises=AssertionError)`, проверяет ожидаемое поведение «бронь не создаётся» |

Примечания:
- Негативный тест один, но параметризован: один сценарий «пустое обязательное поле» запускается семь раз (комната, дата, начало, окончание, участники, имя, почта).
- Дата в тестах всегда «завтра», чтобы результат не зависел от времени запуска (иначе пересекается с BUG-01).
- Тексты ошибок под полями и общего сообщения формы взяты из текущего поведения страницы, в требованиях они не заданы.

## Вопросы и допущения по требованиям

Вопросы, которые я бы задал продакту или аналитику:

1. **Тексты и способ показа ошибок.** В требованиях нет формулировок сообщений об ошибках и способа их показа (под полем, общее сообщение). Какие тексты считать эталонными?
2. **Поле «Ваше имя».** Какая максимальная и минимальная длина и какие символы допустимы? Сейчас имя из 72+ символов выходит за границы блока, а имя из одних спецсимволов принимается.
3. **Рабочая почта.** По каким правилам валидируется формат? Сейчас принимается адрес с двойным `@`. Нужна ли проверка корпоративного домена («рабочая» почта)?
4. **Время и часовой пояс.** По какому времени определяется «прошедшее время сегодня»: по часам браузера пользователя или по времени офиса?
5. **Рабочие часы офиса.** Можно ли бронировать ночное время и всю дату целиком (принимается интервал 00:00–23:59, если снять ограничение по длительности)?
6. **Поведение на проде.** Нужны ли защита от повторной отправки (двойной клик), проверка пересечений броней и обработка ошибок сервера? В демо данные не отправляются и не сохраняются.
7. **Мобильные и локализация.** Поддерживаются ли мобильные устройства и другие локали, каковы минимальные поддерживаемые браузеры?

Допущения, на которых построена проверка:

- Требованиями считается раздел «Ожидаемое поведение» из задания.
- Страница демонстрационная: данные не отправляются и не сохраняются, поэтому серверную валидацию проверить нельзя.
- Приоритеты дефектов оценены в предположении, что серверной валидации нет. Если она есть, приоритет BUG-01, BUG-03 и BUG-04 снижается до P3.
- Тексты сообщений об ошибках взяты из текущего поведения демо-страницы, а не из требований.
- Время и дата берутся по часам компьютера, на котором запущена проверка.

## Проверенные области

- Основной сценарий бронирования и состав сообщения об успехе (комната, дата, время, имя).
- Обязательные поля: все семь по очереди и все сразу, сообщения под полями и общее сообщение формы.
- Вместимость: границы для всех трёх комнат (4/5, 10/11, 20/21), недопустимые значения участников, смена комнаты после ввода участников.
- Дата и время: вчера, сегодня, завтра; прошедшее время сегодня; границы длительности (30 минут, 4 часа); окончание равно началу и раньше начала; бронь через полночь.
- Почта: валидный формат, невалидные варианты (без `@`, без домена, с пробелом, двойной `@`, кириллица).
- Имя: обычное, длинное, из спецсимволов, HTML и JavaScript (XSS).
- Поведение: данные не сохраняются после перезагрузки, данные никуда не отправляются.
- Интерфейс: управление с клавиатуры (Tab, Enter), мобильная ширина, масштаб, тексты сообщений об ошибках.

## Риски

- **Безопасность (BUG-05).** Введённое имя исполняется как код. Сейчас это только «атака на себя», но на проде данные брони видят другие сотрудники, и это превращается в сохранённый XSS: кража сессии, действия от чужого имени.
- **Брони с некорректным временем (BUG-01, BUG-02, BUG-03, BUG-04).** Если серверной валидации нет, возможны брони в прошлом, нулевой и слишком короткой длительности и на сутки. Это ложная занятость комнат, конфликты с другими сотрудниками и риск неверного расчёта стоимости, если она считается по стандартной длительности.
- **Расхождение клиента и сервера.** Вся проверка в демо идёт на стороне страницы. Если на проде валидации нет на сервере, обход интерфейса даёт те же дефекты.

## Ограничения проверки

- Не проверялись отправка данных, защита от дублей (двойной клик) и пересечение броней по времени: в демо нет API и хранилища. На проде это обязательные проверки.
- Только Chromium (Playwright) и Chrome 157.0.8103.79 на macOS 27.2.1. Firefox, Safari и реальные мобильные устройства не проверялись, мобильная ширина смотрелась только изменением размера окна в devtools - toggle device toolbar.
- Нет нагрузочных, кросс-локальных, часовых поясов и доступности (кроме базовой проверки с клавиатуры).
- Автотесты покрывают основной сценарий, обязательные поля и один дефект. Остальные дефекты и граничные значения проверены вручную.
- Дефект BUG-01 не автоматизирован: он зависит от времени запуска и требует управления временем в тесте.

## Рекомендации и дополнительные наблюдения

Эти наблюдения не вошли в пять основных дефектов (в задании лимит), но их стоит учесть:

1. **Плейсхолдер в поле «Участники».** Сейчас «Например: 6», но для комнаты «Малая» (до 4 человек) это значение недопустимо и вводит в заблуждение. Лучше «Например: 3», оно подходит всем комнатам.
2. **Склонение в сообщении об ошибке.** При выборе комнаты «Средняя» (до 10 человек) и значении участников больше 10 показывается «В комнате максимум 10 участника.». Правильно: «участников» (и аналогично для остальных комнат: 4 и 20).
3. **Имя из одних спецсимволов принимается.** Отдельно от XSS: стоит ограничить допустимые символы и добавить обрезку по длине.
4. **Длинное имя ломает вёрстку.** Имя больше 72 символов выходит за границы блока с сообщением. Нужны ограничение длины и перенос текста.
5. **Почта с двойным `@` принимается.** Проверка формата почты слишком слабая.
